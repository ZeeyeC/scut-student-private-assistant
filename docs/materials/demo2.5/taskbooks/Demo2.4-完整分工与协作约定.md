## 4. 最小接口约定

下表是开发约定，**不是 Demo2.4 已有API清单**。R0由责任人先在各领域契约文件中给出精确字段、状态枚举、版本规则与测试样例，再落地实现；复用现有草稿/确认/回执机制，不并行搭建第二套保存系统。

| 接口或记录 | 提供方 | 最低要求与消费方 |
| --- | --- | --- |
| 课程事实区间与冲突结果 | 甲 → 乙 | 稳定课程发生ID、原课日期、分段ID、带时区起止、地点、来源版本；区分重叠/转移不足/耗时未知，标识涉及锁定安排。 |
| 约束草稿及有效约束 | 甲 → 乙 | 硬/软类型、有效期、重复规则、时区、来源、确认状态和版本；乙对话补充同一草稿，不能凭模糊“下午”直接确认。 |
| 执行事实与汇总 | 乙 → 甲 | 任务/步骤/时间块ID、精确计时/补记/历史估算来源、实际分钟、任务完成状态、未执行原因、更正引用、数据版本；缺记录为未知，不转换为0。定义精确记录与历史估算的去重/替代规则。 |
| 偏好与目标读取 | 乙 → 甲 | 已确认值、来源、样本量、有效期、版本；目标包含周预算、期限、负荷类别及暂停状态；未设置值保持未知。 |
| 变化事件 | 双方产出，甲消费重排 | 复用`planning_event`，按事件类型、来源ID及版本生成去重键；新增执行变化、档案/目标变化等类型及处理状态。不得把重排确认事件再次无限触发重排。 |
| 规划/重排/备选方案 | 甲 → 乙 | 输入资料版本、规则版本、范围、影响原因、事实依据、保留/新增/移动/移除、未安排分钟、冲突与风险；确认时重验版本、当前时间及硬约束。 |
| 周计划快照 | 甲 → 乙 | 复用`plan_snapshot`，保留初始版本及后续变更链；乙据此对比原计划、现计划和真实投入。 |
| 主动建议与协商意图 | 乙维护，调用甲服务 | 记录意图版本、备选方案引用、状态、原因指纹、稍后处理/关闭与安静时段；事实版本变化使旧方案失效。 |

共同时间规范：保存时区和可确定的时间点，区间按半开区间处理，跨午夜、跨周、跨年及有夏令时的时区均做边界测试。重复规则保留当地时间语义。模型提取候选与解释，程序负责时间展开、容量、冲突和最终写入。

执行事实变更、截止时间变化、约束/档案/目标变化等影响规划的写入，必须进入既有资料版本机制。开始/暂停等是否影响当前草稿由R0明确；禁止仅保存乙侧新记录而让旧方案继续确认。状态回执、正式修改和事件写入遵守现有事务与幂等机制。
