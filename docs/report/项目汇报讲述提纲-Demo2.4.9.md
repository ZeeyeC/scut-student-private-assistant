# 课间项目汇报讲述提纲（Demo2.4.9）

适用：8–12分钟介绍与演示，另留2–3分钟答问。详细事实、代码与分工见[总汇报](项目汇报-Demo2.4.9.md)和[历史证据](项目历史与甲乙贡献证据-2026-10-30.md)。

**使用前：最终测试数字、当前App路径、提交SHA和发布结果仍须依据本轮实际日志补入。下列时间是讲述安排，不是性能数据；所有60/25/35分钟等数字是隔离业务样例，不是学生真实研究结果。尚未成功构建时，开场应说“当前源码收尾演示”，不能说“正式新版App已验收”。**

## 1. 开场：我们做成了一条什么链路（约45秒）

可以直接讲：

> 我们做的是“课间”，面向大学生的课程、任务和学习安排助手。它把课表和作业变成可校对的资料，在真实空档里安排工作，再把实际投入、临时变化和用户偏好接回下一次规划。学生始终能看到依据，并决定是否保存。
>
> 展示重点有三个：课表是否真的算对时间，计划和实际是否分开，以及变化后能否可靠地调整和撤销。

屏幕准备：本轮实际版本入口、桌宠和“课表”页面；若实际App还未通过发布验收，改用当前可验证源码环境并明确说明。

## 2. 架构：模型、规则和确认分别负责什么（约60秒）

结合总汇报架构表讲四层即可：

1. 原生Swift桌宠和React界面负责轻量入口与详细校对。
2. FastAPI/SQLite保存版本化资料、收据和历史；相同请求重试不重复写，失败回滚。
3. 统一课程展开、冲突、容量和确定性规划处理可用时间，助手与协商都调用它。
4. 模型帮助识别和整理成候选，程序校验后仍须用户批准才成为正式资料。

可以直接讲：

> 课程事实由同一套规则展开。普通排程、助手、目标容量和协商都读同一套事实。未知信息不会被当作零，任务完成也不会自动被算成真实学习分钟。

不展开框架名单和所有API，不把开源库功能说成自研；自研重点是学校适配、学生业务事实、规划规则和可靠确认链路。

## 3. 演示一：课程分段与批量校历（约2–3分钟）

准备资料：隔离样例中两门课、多个原课日期；其中一门含非连续节次。通知名称、依据和作用范围明确标“合成演示”。

| 操作 | 画面中应指出什么 | 讲述句 |
| --- | --- | --- |
| 打开分段课程详情 | 上午/下午授课、课间与中间真实空档 | “课表看似跨度很长，但真正忙碌的是这些段，系统不能吞掉中间空档。” |
| 打开学校校历批量表单，选择两门课、实践日期范围与依据 | 必须明确选课程和日期，不用raw JSON | “实践周或节假日以用户确认的学校通知为准，不按公共假期猜补课。” |
| 生成预览 | 每次课程前后状态、冲突、受影响计划；此时正式课表未变 | “这里还只是草稿，先看清楚哪些课会改变。” |
| 原确认入口保存，再刷新 | 批次生效、来源与历史仍在 | “一批全部成功或全部回滚，网络重试不会重复应用。” |
| 历史中撤销整批，先预览再确认 | 恢复原来的例外，不只恢复默认课表 | “撤销恢复的是这批之前的状态。若有人后来改过其中一课，系统会拒绝覆盖。” |

备用展示：明确原日→目标日补课映射，说明原节次/非连续分段保留；多个原日指向同日时，重叠应真实显示。没有真实学校通知时只讲机制已实现，学校规则专项仍待资料。

## 4. 演示二：计划、实际与更正进入下一方案（约2分钟）

准备资料：一个预计60分钟的步骤，正式计划已有对应安排。执行样例预先保持可重复，避免创建三份相互重复的投入记录。

1. 展示任务预计60分钟与已确认计划。
2. 补记实际25分钟，并明确选择未完成/部分完成及原因。
3. 打开规划依据或重排建议，指出后续剩余35分钟；正式日程在确认前保持原样。
4. 更正原记录为20分钟，查看更正链及下一方案的剩余40分钟。
5. 指出锁定、已开始、完成或未结束计时关联安排受到保护。

可以直接讲：

> 乙负责记录真实做了多少，并保留更正和来源；甲让这些事实真正进入剩余量和规划。它不会把计划60分钟当作已经做了60分钟，也不会把更正前后再加一遍。

若时间紧，只展示一条补记与一条更正；计时恢复作为备用说明。不要为了凑演示把任务状态改成完成后再声称记录了精确分钟。

## 5. 演示三：偏好、目标和协商有实际计算依据（约1–2分钟）

根据现场稳定程度选择其中一条完整展示，另外两条用简短说明：

- **偏好与类型**：用户明确把任务分为deep/review并设置时段偏好，比较下一方案。讲“仅匹配对应工作类型；硬课程和禁排不让位；未知类型保持未知”。
- **目标共享容量**：查看两个目标总预算600分钟与共享容量360分钟，说明240分钟缺口、暂停和reduce/delay/ask许可；不凭预算虚构任务或延截止。
- **复盘与协商**：从周复盘的原计划/改版/实际/未知进入下周意向或协商，连续修改后选择真实方案，先形成原草稿，确认后才生效。

可以直接讲：

> 用户数据不是只留在设置页。已经确认且仍有效的档案、目标和执行会改变计算结果；系统同时保留来源和未知项。我们目前实现的是可解释规则，并没有声称自动学会所有习惯。

## 常见答问准备

| 可能的问题 | 建议回答 |
| --- | --- |
| 为什么不让模型直接排课和保存？ | 模型适合识别与整理；课程占用、版本与写入需要确定规则和明确批准，才能解释、恢复并防止过期方案覆盖事实。 |
| 个性化和时长学习到什么程度？ | 已确认档案和类型参与计算；时长建议限定同一步骤的可靠记录与末次完成，不泛化到其他任务，也没有长期效果数据。 |
| 原生超时是不是完全修好了？ | 本轮隔离并记录具体健康传输边界，控制网络回归和实际App结果分别列出；历史偶发失败不能靠一次通过宣称永不复发。 |
| 批量撤销会不会删除其他改动？ | 撤销核对本批保存后全部例外版本和payload，发现后续修改或新增同次例外就409；通过后精确恢复原状态，保留审计。 |
| 为什么PR仍open还能演示？ | 可运行代码位于版本/联合分支和本地工作树，实际merge发生在分支内；main、PR状态和App交付是不同证据。 |
| 两人贡献怎么衡量？ | 按领域实际实现、接线、界面和验证举例，说明先后依赖与共同闭环，不按提交数、资源帧数或代码行数分百分比。 |
| 当前能否说学校OCR已95%？ | 不能。工具门槛已明确，仍要真实匿名标注和原始预测报告；没有样本时准确率是未知。 |
