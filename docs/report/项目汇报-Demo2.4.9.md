## 一、项目解决什么问题

“课间”面向大学生把课程、作业、长期目标与实际学习过程放到同一条可核对的时间链路中。学生先导入课表和作业，校对任务与截止时间，再确认规划；课程变化或任务没做完时，系统结合真实剩余量和可用时间提出调整，学生保留最后决定权。

项目处理的具体困难包括：课表截图和PDF字段不完整，非连续节次容易误占空档；作业只有一句话却缺少可执行步骤；计划时长与实际投入不同；临时调课、就医或实验安排会使旧计划失效；多个目标争用同一批空档；系统“知道偏好”却未必真正用于计算。项目逐步把这些问题变成显式资料、确定性规则和可确认草稿。

当前源码形成的完整链路为：

1. **确认事实**：本人导入学校课表，补齐学期和节次；课程、固定事项、禁排与校历例外成为正式时间事实。
2. **整理工作**：图片或文字作业先形成草稿，补齐截止依据，拆成有依赖、预计分钟和完成标准的步骤。
3. **计算并解释**：统一展开课程实际占用，扣除硬约束，读取真实执行、目标和已确认偏好，返回计划、未排原因、容量和风险。
4. **明确批准**：课表、课程调整、事项、计划和助手写入均经过原有草稿/批准入口；来源变化时拒绝保存旧方案。
5. **记录实际**：补记或计时记录真实分钟，任务完成状态、未完成原因与旧估算分开；更正保留历史。
6. **持续调整**：课程、执行、档案或目标变化产生事件，合并为可忽略或可确认的重排建议；复盘与协商继续使用同一事实和排程服务。
7. **轻量入口**：原生桌宠提供任务环、无声提醒、课后询问和快捷打开；完整页面承担细致校对与说明。

这套链路能够说明“为什么这样安排、用了什么资料、还有什么未知、确认后改哪些内容”。目前没有真实长期使用对照数据，不能把上述软件能力直接说成已经证明提高成绩或降低压力。

## 二、系统架构与工程原则

| 层次 | 当前技术和职责 | 自有实现重点 |
| --- | --- | --- |
| 桌面入口 | macOS Swift / AppKit / WebKit，原生桌宠与助手窗口 | 动画和任务环、提醒、课后询问、后台启动/停止、资料身份与健康/能力检查 |
| 业务界面 | React / TypeScript、TanStack Query、FullCalendar、assistant-ui、Radix等组件 | 草稿校对、课程分段、任务步骤、执行计时、容量风险、档案目标、复盘协商及错误恢复 |
| 业务服务 | FastAPI / Pydantic、SQLAlchemy / SQLite、Alembic | owner隔离、版本化Resource、幂等Receipt、原子事务、不可变历史、统一课程与规划领域服务 |
| 规划事实与计算 | 统一课程展开、冲突、禁排、容量、确定性规划和局部重排 | 实际占用、已知跨校区耗时、剩余工作、目标共享容量、偏好/负荷、保护已有事实与未排解释 |
| 模型协作 | Deep Agents / LangChain / LangGraph、统一模型网关、SSE与SQLite检查点 | 图片/PDF/文字转结构化候选、追问、工具审批与恢复；正式写入仍由程序验证并批准 |
| 学校导入 | WXT / MV3扩展、本人浏览器登录、已适配学校页面读取 | 华工个人课表DOM适配、来源与完整性校对，避免保存学校账号密码 |
| 构建交付 | 当前版本独立构建、冻结服务验收、应用/源码ZIP、manifest和SHA256 | 从当前工作树构建，保留失败证据；不复制旧App冒充新版，不将配置/Key/个人资料装入交付包 |

核心数据复用已有 `Resource` 和 `Receipt`，新增领域尽量扩展经校验的资源负载，而非为每项功能建立另一套数据库。规划器读取同一套课程、例外、约束和执行事实；助手、协商、目标页与重排调用这些服务，避免多个界面各自“算一遍空档”。

可靠性约定贯穿各层：未知不当成0，任务完成不补造真实分钟，软偏好不越过硬约束；每次确认绑定来源与资源版本，重放同一请求不重复计时/写入/生成事件；事务失败整批回滚；锁定、完成、已开始或未结束计时关联的安排受到保护。模型不可用时，已有课表查询、执行记录和规则规划仍有独立代码路径。

## 八、Demo2.4.9本轮收尾做了什么

本轮依据[当前收尾设计](../superpowers/plans/2026-10-30-project-completion-design.md)沿原有架构推进，由代理辅助实现与整合。以下按已存在的代码说明变化；各项联合验收和实际App结果见第十一节，不将本轮自动化工作直接冒充两位同学既往手写历史。

### 1. 学期规则、多课程批量调整与精确撤销

新增 `semester_contracts.py`、`semester_calendar.py`、`semester_routes.py` 和 `SemesterCalendar.tsx`，复用原草稿确认、exception、课程展开和规划事件。用户明确选择实践周/学校节假日/补课/自定义规则，填写通知依据、课程和原课日期范围，或逐项原日→目标日映射。

预览列出实际发生的每次课程、前后时间、冲突和受影响计划；补课保留原授课/课间/非连续分段。确认以批次原子保存，绑定来源版本、payload和完整预览hash，并保留before/after审计。撤销先生成新草稿，检查本批全部保存后状态；后续修改或同次新增例外会409，避免覆盖用户之后的调整。原有多个active/inactive例外按原payload恢复，不用简单删除全部调整代替撤销。SQLite savepoint同时防护外层确认失败回滚。

软件通用规则和真实学校规则的验收分别判断：本轮没有凭空生成真实实践通知或学校节假日安排。详见[校历契约](../contracts/semester-calendar-v1.md)。

### 2. 显式类型、任务难度和课程准备规则

`study_types.py` 与 `StudyTypes.tsx` 为课程类型、任务工作类型和难度提供显式确认、版本与历史；旧课程/任务没有分类时继续返回未知，不由名称、OCR或模型补写。分类使用独立资源，避免重新导入课表时无意重置用户标注。

统一规划输入读取分类后，deep/review等偏好用于对应工作类型，难度作为明确排序依据之一；课程准备/复习候选可按用户明确的课程类型规则和分钟数生成，并使用既有确认、去重、拒绝和来源失效机制。类型和难度不创造硬空档，用户未指定的准备分钟仍未知，不能声称已经建立复杂认知模型。

### 3. 原生健康检查的可定位传输边界

`LocalHealthTransport.swift` 为固定本机 `127.0.0.1` 的health端点提供独立探测，记录请求阶段、耗时、状态和错误码等诊断；隔离代理、缓存、cookie、凭据与旧连接复用，不跟随重定向，保留原有服务身份和能力门禁。新后台能力标识需与本次App同步，避免复用缺少新业务能力的旧后台。

可控网络测试、原生逻辑和实际App联调应分别留下结果。该修复针对可观察的传输/配置边界；既往偶发超时并未被本报告宣称已经穷尽所有根因。失败证据和发布原有的有界复跑政策继续保留，不用反复重试代替诊断。

### 4. 不调用模型的OCR离线验收工具

`timetable_benchmark.py` 与 `scripts/evaluate-timetable-benchmark.py` 接收人工核对的匿名标注和对应原始预测，按显式slot ID配对，检查重复样本/hash，分开真实、合成与不合格真实元数据；输出姓名无关的样本标识、漏识/多识、逐字段分母、正确/错误和准确率，以及布局和输入类型覆盖缺口。

门槛按至少30份合格匿名真实样本、5种布局、图片/文字PDF/扫描PDF覆盖及关键字段95%判断，人工修正后的预测不能冒充原始识别结果；零分母保持未知，不算100%。工具只做离线评分，不打开用户原图/数据库，不联网调用模型，也不能仅凭自报元数据证明样本真实。真实标注与样本来源仍需人工审查。

### 5. 总汇报和独立交付

本轮另形成可核实历史报告、当前总汇报与讲述提纲。最终按既有发布流程从当前工作树生成App、应用ZIP和源码ZIP，附使用说明、验证结果、manifest及SHA256；是否真正产出和通过校验见第十一节。已有源码目录、正式归档、配置、个人数据、备份及失败暂存继续保留。
