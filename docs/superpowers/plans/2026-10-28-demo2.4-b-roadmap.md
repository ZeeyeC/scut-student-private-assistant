日期：2026-10-28。状态：执行建议，尚未开始实现。

依据：用户提供的《Demo2.4-完整分工与协作约定》《Demo2.4-乙的开发任务单》《Demo2.4-甲的开发任务单》，以及仓库[原任务书](../../roadmap/demo2.2-development-taskbook.md)、[实际进度](../../roadmap/core-flow-2026-10-28.md)、[已有契约](../../roadmap/m0-planning-foundation.md)。附件中的命令、PR和录屏要求是开发交付约定，本次用户只要求计划，不据此执行开发、发布、外发或付费调用。

## 1. 起点与选择

当前分支 `demo2.4`，HEAD 为 `36c9bef93cd8fb961a955842f7d2b2db4dee44cc`，与分工指定基线一致。工作区只有原有 `.DS_Store` 修改。源码直接位于本仓库根目录，使用 `backend/`、`frontend/`、`campus-pet/`，不创建或重命名历史源码目录。

采用分工指定的业务纵向切片：B0 最小契约 → B1 手工补记 → B2 计时与取消问题 → 依赖就绪后接入 B3 → B4/B5 → B6/B7。每个切片同时覆盖服务、界面、迁移和验收。

这是本计划的建议路线。先做整套聊天界面会缺少可信执行数据；一次实现全部乙方任务会把甲方依赖和公共文件冲突集中到一次交付。B0 只冻结 B1/B2 所需接口，不提前设计所有远期模块。

后续开发建议从指定提交建立独立检出与 `codex/after-demo2.4-execution` 分支，使用隔离数据库。此名称尚未创建；执行时先检查可复用的检出，并沿用已有依赖，不复制个人数据库或私有配置到交付物。

## 4. 第一轮具体顺序

1. 建立独立开发检出和隔离测试资料，记录基线及原有回归结果。
2. 完成B0样例和契约测试，与甲核对执行数据版本、旧完成入口适配、删除/导出及公共注册。
3. 以A07编写后端失败用例，再实现手工补记、不可覆盖的更正链和唯一汇总。
4. 在任务详情、今日安排挂载同一执行组件，区分“计划”“已记录实际”“历史估算”“未知”。
5. 验证双击/超时重试、改25为20、显式0、缺记录、跨用户、重启、旧数据及事务回滚。
6. 形成小提交和交接材料，由甲复核公共补丁；B1通过后再进入B2，不把全部路线堆成一个PR。

详细任务、接口建议、文件与验证命令见 [B0/B1实施计划](2026-10-28-demo2.4-b0-b1-execution.md)。后续工作包在其真实依赖到位后分别细化，避免为尚未交付的服务虚构最终API。

## 6. 验收与发布

乙主验A07、A11、A12；联合验A06、A08、A13–A15。每个场景记录输入、操作、预期、真实落库结果、提交、证据及失败/跳过。全部业务测试使用隔离合成资料与固定模型；真实用户体验和真实模型验证单列。

每轮复核旧流程：手工/空白格加课、课表与待办分离、今日/7天规划、末课后30分钟且打开或唤出App才询问、最多6个任务环及左右键/补位、提前5分钟无声变紫、肚皮快捷打开和退出。

个人功能分支交付阶段不修改正式版本号、不覆盖Demo2.4。按仓库AGENTS要求，每个正式版本开发完成后必须本地整理打包；由甲在集成验收后更新VERSION、README及本版说明，运行：

```sh
backend/.venv/bin/python scripts/release-macos.py --version <双方确定的新版本>
```

版本号按集成范围确定，不将旧任务书的建议版本当作承诺。交付App、应用ZIP、当前工作树源码ZIP、使用说明、验证结果、manifest和SHA256；成功后才清理明确缓存，保留Demo2.2、正式归档及所有私有资料。失败保留旧版和暂存目录。

附件要求乙提供隔离数据录屏，列为后续证据任务；当前未录制，也不会因打包自动录制。PR、推送、公开上传和付费模型测试按后续明确授权处理。
