# 乙方 B0/B1：实际执行补记 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking. 用户已于2026-10-28指令执行，采用本会话逐项实施及末次独立复核；首轮代码和本地功能验证已完成，甲方复核及原生窗口完整验收仍待完成。

**Goal:** 独立交付“计划60分钟、实际25分钟、任务未完成”，并使更正、历史估算、幂等、重启和计划失效均可信。

**Architecture:** 在既有Resource/Receipt/SQLite事务内新增执行领域记录，执行事实采用追加更正链，统一服务产生汇总及兼容投影。乙提供独立契约、路由和前端组件；公共后端与旧时间块完成适配由甲集成。保持计划分钟、实际投入、任务完成及历史估算四种语义独立。

**Tech Stack:** Python 3.12、FastAPI、Pydantic、SQLAlchemy/aiosqlite、pytest；React 19、TypeScript、TanStack Query、Vitest、Playwright；原生桌宠Swift。使用已有锁文件和依赖，不新增服务。

**Spec:** 用户提供的《Demo2.4-乙的开发任务单》B0/B1、《Demo2.4-完整分工与协作约定》S01/S02及接口/文件归属；仓库[原任务书T10/S01/S02/A07](../../roadmap/demo2.2-development-taskbook.md)、[当前事实](../../roadmap/core-flow-2026-10-28.md)。完整范围及其余阶段见[乙方路线](2026-10-28-demo2.4-b-roadmap.md)。

## Global Constraints

- 共同基线：`demo2.4`，`36c9bef93cd8fb961a955842f7d2b2db4dee44cc`；当前源码根目录不改名。
- “缺记录为未知，不转换为0”；显式补记0分钟与缺记录必须不同。
- “桌宠右击只完成任务，不伪造实际时长”；打开网站或文件也不代表完成。
- “历史完成时长只标估算”；不能从计划起止或完成按钮推导精确投入。
- “状态回执、正式修改和事件写入遵守现有事务与幂等机制”；不建第二套保存机制。
- 执行事实影响既有资料版本；不能保存新事实后仍允许确认旧计划。
- 时间保存IANA时区及可确定时间点，区间采用半开区间；手工补记的日期来自用户设置时区。
- 公共后端及`planner.py`由甲集成；公共前端由乙集成；生成API、锁文件及发布版本由甲统筹。
- 使用隔离合成资料，不读写个人数据库或Key，不自动付费调用、外发、PR或录屏。
- 本轮不包含自动计时、重排算法、档案、目标、周报、主动建议或协商；分别按路线后续实施。

## Review Focus

1. 保存响应丢失后重试：复用同一操作键只生成一个事实与事件；更换键也不能再次创建同一逻辑执行，见任务2/4。
2. 旧完成入口与新补记交错：同一覆盖范围的60分钟估算被25分钟实际取代，不能变成85分钟，见任务1/3。
3. 更正与删除、重新拆解、跨用户或版本变化竞争：要么原子成功，要么明确冲突，无孤儿事实和半更新，见任务2/3/5。
4. 缺记录、显式0、只有历史估算：界面和读取契约必须区分，跨午夜/跨年按已保存时区归属，见任务1/4/5。
5. 事实写入或事件保存中途失败：事实、更正、投影、版本及回执同事务回滚；原计划和旧资料保留，见任务2/5。

## Task 1: B0 最小契约与固定样例

**Files:** 新增`backend/app/execution_contracts.py`、`backend/tests/test_execution_contracts.py`、`docs/contracts/execution-v1.md`。

**Interfaces:**

- Produces: `ExecutionWrite`、`ExecutionCorrection`、`ExecutionView`、`ExecutionSummary`（Pydantic模型）；甲乙共享的`execution_changed`事件样例。
- 拟定写入字段：`client_operation_id`、`execution_id`、`task_id`、可空`step_id/plan_block_id`、关联资源预期版本、`performed_on`、`timezone`、整数`actual_minutes>=0`、`feedback`、可空`unfinished_reason`、可空`task_status`。`task_status`为空保持任务状态，不能依据分钟自动完成。
- `feedback`建议枚举为`partial/completed/not_started/skipped`，表示本次执行反馈；`unfinished_reason`为`interrupted/insufficient_time/unsuitable_schedule/skipped/other`或空。B2计时状态另行扩展，不能重载任务完成枚举。
- `ExecutionCorrection`引用原事实ID及预期版本，替换该逻辑执行的分钟/反馈并保留原记录；同一更正链仅当前有效版本参与汇总。
- `ExecutionView`使用既有Resource包络；data含`schema_version`、来源`manual/timer/legacy_estimate`、关联、逻辑执行ID、更正引用及有效状态。B1只生成manual，不把旧值改写成timer。
- `ExecutionSummary`含`task_id`、可空`step_id`、`actual_minutes: int|null`、`legacy_estimated_minutes`、`planning_spent_minutes`、覆盖/缺口标记、有效记录ID、更正链引用和全局`source_revision`。缺记录的actual为null，用户明确记录0则为0。
- 覆盖规则：同一`execution_id`仅有效更正计一次；不同明确执行才相加。能定位到同一时间块的历史估算由真实记录替代，不能再次累计。来源不明的旧步骤总量保留为未分配估算，禁止假装能定位到某次执行；覆盖不明确时需用户核对，不静默相加。
- 事件复用`record_change(db, owner, "execution_changed", source_id, source_revision, details)`；去重键和事件处理状态遵循甲方公共机制。B1记录事件，甲T11消费后才产生重排建议。
