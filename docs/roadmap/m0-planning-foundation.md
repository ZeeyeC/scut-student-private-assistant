## 使用方法

进入“待办与日程 → 禁排时段 → 添加禁排时段”，填写名称和起止时间，生成草稿。校对后两步确认，时段才生效。名称可只写“不可安排”，无需填写私人事由。

时间按已保存的设置时区解释，与电脑当前时区无关；支持跨午夜。夏令时不存在或重复的本地钟点会明确报错，不静默猜测。首版只接受单次硬约束，重复规则和软偏好尚未实现。

已保存的禁排可修改、停用和重新启用。修改要再次校对和确认；修改已停用的条目不会顺便启用。停用保留历史，不删除旧记录。

保存禁排不会直接改动正式计划。点击“智能安排未来 7 天”，查看避让时段、安排原因、新增/保留/替换数量和未安排分钟，再确认新计划。若与锁定任务冲突，保留锁定任务并告警，不将冲突安排算成有效进度。课表页面只显示课程；禁排以灰色条目出现在“待办与日程”，不进入桌宠任务环，也不触发紫色提醒或快捷打开。

## 已落地数据契约

继续使用现有 `Resource` 包络：`id / owner_id / kind / revision / data / created_at / updated_at`。归属与版本在服务端校验。所有写请求通过既有 `Receipt` 保存幂等回执；业务事务使用 `BEGIN IMMEDIATE`，仅支持单个 SQLite 服务进程。

### scheduling_constraint

`data` 包含 `title`、`strength=hard`、`recurrence=once`、IANA `timezone`、带时区的 `starts_at/ends_at`、`active`、`confirmed=true`、`source={kind:manual,draft_id}` 和 `confirmed_at`。区间为半开区间 `[start,end)`，以实际 UTC 时刻比较先后。只有已确认且启用的条目进入排程；不会套用课程缓冲来扩大用户指定的禁排区间。

约束草稿为 `draft_kind=scheduling_constraint`，负载为 `{constraint, constraint_id, constraint_revision}`。后两个字段必须同时为空或同时给出。修改已有约束时，草稿绑定目标和原版本，校对不能将它换成别的目标或跳过版本保护；确认时再次检查目标版本。创建草稿本身不改变约束或正式计划。

| 接口 | 用途 |
| --- | --- |
| `GET /api/scheduling-constraints` | 查看本人的已保存约束，包含停用项 |
| `POST /api/drafts/scheduling-constraint` | 新建或发起对已有约束的修改草稿 |
| `PUT /api/drafts/{id}` | 修改原草稿内容，必须带草稿版本 |
| `POST /api/drafts/{id}/confirm` | 确认保存；修改已有条目时同时检查约束版本 |
| `PATCH /api/scheduling-constraints/{id}` | 显式启用/停用，必须带当前版本 |

### planning_event

`data` 包含 `schema_version=1`、`event_type`、`source_id`、`source_revision`、`dedupe_key`、`occurred_at`、`status=recorded`、`details`。目前事件为 `constraint_changed` 和 `plan_confirmed`；前者保留修改前后资源，后者引用批准快照。标识由用户、事件类型、来源标识及版本确定，同一事实不会再次入库。

事件与正式资源、幂等回执在同一事务内保存。`recorded` 只表示事实已记录，不代表已经执行重排。本批没有事件后台消费者、自动任务或消息队列；重启不会丢失事实，也不会触发模型调用或自行改日程。T11 增加消费流程时须另行定义处理状态、重试和建议去重。

### plan_snapshot

`data` 包含 `schema_version=1`、`draft_id`、`approved_at`、`rule_version`、全局输入 `source_revision`、`inputs`、`previous_blocks` 和 `approved_plan`。每个被批准的草稿只创建一个快照，保留当时课程展开、固定事项、任务、步骤、设置、约束与原计划数据；后续重排另建快照，不覆盖原快照。

快照只在正式批准时保存，和正式时间块替换共用事务；批准失败不会留下半份快照或计划。生成建议仍沿用原有待确认草稿。新计划产生 `explanation`（规则版本、任务/步骤、依赖和约束版本、实际分配依据）、`protected_windows` 及 `changes`。相同步骤、起止时间不变时复用原条目标识，保留其日程快捷设置。

新代码仍可确认合法的 Demo2.2 旧计划草稿：规则版本记为 `demo2.2`、缺少的输入快照记为 `null`，不补造历史。任何正式资料变化都会递增既有全局版本；在此之前生成的计划不能跨版本保存。

## 兼容 备份与恢复

本批新增的是 `Resource.kind` 与新记录负载，不修改 SQLite 表结构，Alembic 仍停留在 `0002`，无需新增物理迁移。启动不批量回写旧课表、作业、设置、模型连接、资产或估算耗时，也不创建默认睡眠/偏好/校历。只有用户的明确操作才新增约束、事件和快照。接口以空列表表示“没有约束”，不把空列表当成用户确认的作息。

现有停服备份会完整包含业务数据库、检查点及上传 PNG，因此自然保留新增记录；恢复仍只允许空目录。测试覆盖合成 Demo2.2 资源启动前后逐行一致、新增约束后的重启以及升级数据的备份恢复。现有真实资料和 `.env` 未用于测试。

需要切回旧 App 时先停止当前后台，再切换；旧版排程器不理解新约束，旧版生成计划不会遵守它们。已有新版备份应保留，不能把仅更换旧程序当成数据回退。

## 华工识别样本准备

先适配已有华工本科个人课表，再扩展华工导出/打印的常见形式。第一批样本类别：周网格原始截图、长表/课程清单截图、文字PDF、扫描/拍照PDF、含分段周次及单双周的混合布局。真实模板由样本确认，不能将五种类别当作已经收集到五种布局。

标注格式至少保留 `sample_id`、来源类型、页号、匿名化状态、课程原文、字段答案、证据区域、待追问字段、期望展开结果。证据区域用页内归一化坐标，不绑定屏幕像素。模糊项的答案可为“需要追问”，不能用猜测值作为真值。

本批没有调用真实识别模型、上传个人课表，也没有声称达到 30 份 / 5 种布局 / 95% 准确率。真实标注集与上传授权需在 T01 进入真实模型评测前落实。仓库中的 `backend/tests/fixtures/scut-timetable/week-cases.json` 为合成周次样例，不计入 OCR 样本量；`pending-scenarios.json` 明确列出仍待实现的例外展开场景。
