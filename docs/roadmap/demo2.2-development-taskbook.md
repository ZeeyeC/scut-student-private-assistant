# 奶蛙助手后续开发任务书

基于 Demo2.2 的识别 规划 执行与对话能力建设

编制日期：2026年10月28日　文档版本：1.0

适用对象：产品负责人、开发人员与测试人员。开发基线：Demo2.2，App 版本 2.2.0，源码提交 ec5ee94c42f1bdbb79e0f6a29a07607ac7b115be。

## 一 建设目标与范围

在 Demo2.2 上逐步补齐课表识别、日常约束、个性化规划、执行反馈和主动协商，使用户能够少录入资料、理解安排原因，并在计划变化时获得可核对的调整方案。复用现有课表、待办、日程、模型调用、草稿确认和桌宠架构，按阶段交付。

第一阶段以可靠输入和约束为重点；第二阶段形成未完成任务和调课后的重排闭环；后续增加用户模型、目标预算、周复盘和主动建议。所有新增能力以具体场景验收，既有测试数量不作为新需求的完成比例。

### 现有能力与建设边界

| 领域 | Demo2.2 已有基础 | 后续建设重点 |
| --- | --- | --- |
| 输入 | 华工网页课表导入、手工与空白格添加课程；作业截图识别 | 图片和PDF课表识别、歧义追问、异常学期规则 |
| 规划 | 未来7天确定性排程，避开课程与固定事项，支持学习窗口和时间上限 | 生活约束、偏好评分、可解释的方案比较 |
| 执行 | 完成状态、时间块投入记录、手动重新规划 | 实际执行记录、自动生成重排建议、周复盘 |
| 对话与桌宠 | 任务和日程对话、校对确认、待办环、紫色提醒与快捷打开 | 持续约束、多轮协商、主动发现负荷问题 |

本轮规划以本地个人使用的 macOS Apple Silicon 版本为主。账号体系扩展、多端同步、其他学校专用适配、地图实时路况、Intel和Windows原生验收另行立项；不阻碍通用图片/PDF输入和手工校区耗时配置。

### 交付原则

自动识别产生候选，自动调整产生建议。课程、锁定安排、完成事实和已确认硬约束优先；正式新增、移动或删除安排前展示变化并由用户确认。不得通过更换模型或增加提示词替代持久化约束和确定性检查。

## 二 识别与结构化任务

本层验收重点是课程时间是否可信。已有图片识别服务针对作业，新增课表识别须使用独立的数据契约和校对流程。

### T01 图片和PDF课表识别

**优先级 P0　依赖 S01与S02**

工作内容：支持拍照图、截图及PDF，区分文字PDF和扫描PDF；提取课程名、教师、教室、校区、星期、周次、节次及适用学期。保存来源页码、证据区域、原文和逐字段不确定状态；多页结果可合并去重。识别结果进入课表草稿，复用现有差异校对及确认保存。

验收条件：建立不少于30份、至少5种布局的人工标注样本，覆盖图片、文字PDF和扫描PDF。可辨认的课程名及排课关键字段归一化准确率分别不低于95%；缺失和歧义字段全部进入待确认，关键时间未确定的课程不得保存为有效排课。报告每个字段的分母、错误及人工修正，不只报告整体平均值。

交付物：输入流程、课表识别服务、证据校对界面、样本集说明与评测报告。图片沿用现有大小和像素限制；PDF首版建议上限20MiB和10页，超限或加密文件明确提示，不静默截断。

### T02 非标准周次和学期例外

**优先级 P0　依赖 S01**

工作内容：复用单双周及周次展开，补充分段周次、连堂、调课、停课、实践周和节假日调整。学期校历必须由用户提供或确认，保留规则来源、作用范围和撤销入口。连堂与中间休息分开表达，非连续节次不得合并成连续占用。

验收条件：单双周、分段课程、跨周调课、整周实践、同一天多门调课和节假日补课均有固定样例；重新导入不重复创建课程。校历缺失时询问，不按公共节假日直接推算学校补课安排。

交付物：学期例外规则、课程展开回归、可追溯的调整记录。

### T03 冲突检测与歧义追问

**优先级 P0　依赖 T01与T02**

工作内容：检测课程重叠、与固定事项冲突、跨校区间隔不足。跨校区先采用用户确认的地点和耗时矩阵；未知地点标记待补充。把影响排课的模糊信息整理成简短问题，答案回填原草稿，保留未解决项。

验收条件：同一时段两门课必须标出；配置转移需40分钟而仅剩10分钟时告警，未知耗时不得显示“可达”。回答“第3周开始”后仅更新对应课程；刷新后仍保留问题、答案及草稿版本，未确认草稿不修改正式课表。

## 三 从课表到日程任务

固定课表提供课程事实，日程根据事实和生活约束安排任务。所有时间计算基于已保存时区和学期配置。

### T04 硬约束与软偏好模型

**优先级 P0　依赖 S01与S02**

工作内容：统一表示课程、固定事项、睡眠禁排、指定日期禁排、通勤和锁定任务；另行表示学习时段偏好、复习间隔和放松偏好。每条约束记录类型、有效时间、重复范围、来源、版本及是否由用户确认。用户可查看、停用和修改。

验收条件：用户确认“周三14点到17点不可安排”后，新方案不得占用该时段；偏好和截止冲突时可提出放宽建议并说明原因，但不得静默突破硬约束。冲突无解时报告不可安排部分，禁止擅自延长截止时间或移动课程。

### T05 自动补充日常安排

**优先级 P1　依赖 T03与T04**

工作内容：根据用户确认的作息，提出早餐、午餐、午休、通勤和课间转移建议。为课程增加可编辑的类型标签，按用户确认规则提出实验预习、课后复习和考试准备时长；数据不足时询问或保留候选。展示空闲时段供自习、社团或运动选择。

验收条件：早课早餐、跨校区出发、午休保护、实验预习各有一条完整场景；重复生成不叠加重复事项。用户拒绝某项建议后不反复添加。休息和空闲时段不默认填满，自习与社团候选不会未经确认变成正式任务。

交付物：作息设置、可解释的规则建议、候选时段界面及去重机制。

### T06 可解释的规划与方案比较

**优先级 P0　依赖 T04**

工作内容：扩展现有排程器，先验证硬约束，再以可配置规则评价偏好满足度、截止风险、负荷和安排变动量。保留现有7天范围；每个新时间块输出事实依据、约束依据和取舍理由，展示新增、保留、移动、移除及未安排项。

验收条件：同一输入和规则版本产生可复现结果；候选方案均无硬约束冲突，排不下的任务给出缺少的分钟数及主要阻碍。解释必须引用实际数据，例如“周五测验前完成，且周四晚符合已设置偏好”，不得生成数据库中不存在的测验或习惯。

交付物：规划结果契约、方案差异界面、解释依据及容量不足测试。首版采用可检查的规则与评分，不要求引入独立机器学习模型。

## 四 个性化规划任务

用户模型先依赖明确设置，再逐步利用执行记录。样本不足时保持现有规则，不把模型猜测记录成用户习惯。

### T07 用户偏好与精力档案

**优先级 P1　依赖 T04**

工作内容：增加偏好学习时段、复习间隔、专注块与休息长度、每天负荷、休闲保护和粗粒度精力时段。区分用户直接设置与系统建议；显示建议依据、使用样本量、有效时间和修改入口。

验收条件：设置“晚上适合深度学习”后，在其他约束相同的对照场景中优先安排深度任务；用户修改设置后下一方案生效。无执行历史时明确采用用户设置或默认规则，不声称已经了解习惯；档案可重置且不会删除课程或任务。

### T08 目标与每周时间预算

**优先级 P1　依赖 T06与T07**

工作内容：支持四六级、考研、健身等通用目标，记录目标期限、子任务、周预算、优先级、任务类型及允许的调整范围。先检查可用容量再拆分周计划；学习与运动使用不同负荷类别，均避开硬约束。

验收条件：某周只剩6小时而目标要求10小时，必须展示4小时缺口及缩减或延后的建议；不得挤占课程、睡眠或自动提高上限。目标任务和临时作业竞争时给出取舍，目标暂停后不再创建新安排，已经完成的事实保留。

### T09 个性化排序与动态减负

**优先级 P1　依赖 T07与T08及T10**

工作内容：按确认的精力、任务难度、截止压力、周预算和当天课量选择学习时段；记录预计与实际耗时偏差，生成可调整的耗时建议。课多时降低可调整任务负荷，空闲周在目标预算内补充任务。

验收条件：使用相同课程与任务、不同用户档案，对照方案体现时段和负荷差异，且都满足硬约束。耗时建议可拒绝或恢复，不因一次延误形成长期结论；缺样本时不自动改变档案。每次变化提供具体理由和对截止风险的影响。

交付物：用户档案设置、目标预算视图、个性化评分规则、对照样例和解释报告。

## 五 执行与反馈任务

执行记录用于说明发生了什么。任务完成、时间块完成、实际投入和未执行原因分别保存；打开文件或网站不能推断任务已完成。

### T10 实际执行记录与轻量反馈

**优先级 P0　依赖 S01与S02**

工作内容：支持开始、暂停、结束、补记实际分钟数及未完成原因，原因包括被打断、时间不够、安排不合适和主动跳过。明确时段结束未反馈、部分完成、任务完成等状态。兼容已有时间块完成时按计划时长记投入的规则，旧记录标注为估算来源。

验收条件：计划60分钟、实际投入25分钟、任务未完成时分别保存正确；重复结束和重试不重复累计。桌宠右击仍只完成整个任务，不虚构实际学习时长；历史记录不升级成精确计时。用户可修正补记并保留更正记录。

### T11 自动生成重排建议

**优先级 P0　依赖 T04与T06及T10**

工作内容：任务时段结束仍未完成、课程调整、新增固定事项或用户请求时，按影响范围重新计算后续安排。合并短时间内重复变化，优先减少已确认安排的移动；保留课程、完成事实和锁定任务。仅在原因或结果发生有效变化时提出新建议。

验收条件：未完成任务可进入下一可行时段；调课后仅调整受影响及相关依赖，展示前后对比。新硬约束与锁定任务冲突时标记待处理，不移动锁定项。确认时重新检查资料版本，过期方案拒绝保存；容量不足和逾期不自动改截止日期。

### T12 周复盘与拖延分析

**优先级 P1　依赖 T10与T11及T07**

工作内容：按周汇总计划分钟、实际记录分钟、任务完成、未执行及数据缺口；区分原始计划与后续改版。连续拖延先提出可核对原因，再建议拆分、换时段或调低负荷。下一周优化先生成建议，再由用户采纳。

验收条件：重排不会覆盖本周原始计划；缺少执行记录显示“未知”，不按0分钟计算。周报数字可追溯到任务和执行记录，重复时段不重复统计；不足以判断原因时追问，不把拖延归因于缺乏自律。采纳建议后可核对下周变化。

## 六 主动性与对话任务

对话统一调用已定义的查询、约束和规划服务，保留现有版本检查、真实回执和保存前确认。相对日期按用户时区和当前消息日期解释。

### T13 自然语言约束落地

**优先级 P0　依赖 T04与T11**

工作内容：把“这周三下午别排事”“下周开始每周五晚上留空”转换为带时间、有效范围和重复规则的约束草稿。查询受影响任务，给出调整建议。缺少具体起止时间时询问，或展示待用户确认的解释，不悄悄采用默认下午时段。

验收条件：用户确认周三14点到17点不可安排后，约束重启仍生效；取消后可重新参与规划。“这周”和“下周”跨年、跨时区均正确。多轮补充修改原草稿，不重复建约束；医院等私人事项可只保存“不可安排”，不要求记录事由。

### T14 主动发现与提前建议

**优先级 P2　依赖 T08与T11及T12**

工作内容：发现近期多项截止、剩余耗时超过空闲容量、课程调整、任务预计来不及等情形，提出有依据的行动建议。扩展现有提醒，按任务准备和通勤提前量提示；保留当前开始前5分钟的无声紫色提醒。

验收条件：三项作业集中截止时，按截止风险、依赖和剩余耗时排序并说明理由；“还有20分钟”必须基于真实空档。相同问题不重复提醒，支持稍后处理、关闭该类建议和安静时段。桌宠不发声音，点击提醒仍遵守用户设定的快捷打开方式。

### T15 多轮协商与替代方案

**优先级 P2　依赖 T06与T07及T13**

工作内容：理解“周五想放松，但周六考试要保住复习”中的目标和取舍，提供至少两个有效方案，展示剩余负荷、截止风险及移动事项。支持“少排一点”“保留这一项”等连续修正，对已确认事实保持一致。

验收条件：多轮对话共同修改同一规划意图，刷新后可继续；选择方案前正式日程不变。无可行方案时明确指出互相冲突的条件并请求选择，不能编造空档或自行牺牲硬约束。取消协商后保留原日程和用户此前确认的约束。

## 七 共同基础与工程任务

### S01 数据契约与事件基础

**优先级 P0　作为各阶段前置工作**

扩展现有资源和版本机制，定义下列记录及其关系。模型负责提取候选、归纳问题和生成说明；时间展开、冲突检查、容量计算、版本校验和正式写入由程序执行。首版保留单进程SQLite架构，采用可恢复的事件记录，不引入独立消息队列。

| 记录 | 必须包含的关键内容 |
| --- | --- |
| 识别来源与疑问 | 原文件引用、页码或证据区域、原文、字段候选、待确认状态、答案 |
| 约束与用户档案 | 硬或软类型、时区、有效范围、重复规则、来源、确认状态、版本 |
| 目标与预算 | 期限、周预算、关联任务、优先级、负荷类别、暂停状态 |
| 执行与更正 | 任务和时间块、实际起止或分钟、来源、原因、修正引用 |
| 计划快照与变更 | 输入版本、规则版本、前后差异、事实依据、批准状态、原始周计划 |
| 变化与提醒记录 | 事件标识、触发原因、影响范围、去重键、处理状态、已提醒状态 |

验收条件：同一变化重放不会重复建任务、累计投入或提醒；重启后恢复未完成建议。正式保存与版本检查在同一事务内完成，失败不留下半份计划。

### S02 资料迁移与原功能回归

**优先级 P0　覆盖全部版本**

为旧资料提供明确默认值和备份恢复流程。升级不伪造偏好、校历或执行事实，不删除已有课表、任务、模型连接和原始资料；模型服务不可用时仍能查表、记录完成和进行规则排程。

必须保留：原手工添加与空白格添加课程；最后一节课结束30分钟后、打开或唤出App才询问作业；课表与待办日程分离；当天已安排任务环最多6项、左击详情、右击完成及稳定补位；无声紫色提醒和肚皮快捷打开；原有动作与安全退出。

验收条件：用合成旧版数据库完成升级、重启、备份恢复和重复执行；原生、浏览器与后端既有回归通过，新增测试验证真实业务结果。

### S03 阶段交付与验证证据

**优先级 P0　每个里程碑执行**

每阶段交付源码PR、可运行App、更新说明、迁移说明、测试报告、隔离资料的真实录屏及包校验值。报告区分自动功能演示、真实鼠标操作和外部实测；沿用隔离数据库和测试模型，真实模型调用另记费用和范围。报告失败、跳过及未验证的平台，不以单次演示替代回归验收。

## 八 阶段与交付顺序

P0为可靠性和核心流程必须完成项；P1为日常体验和个性化能力；P2为依赖执行数据的主动协商。版本名为建议命名，正式发布时间在各阶段验收后确定。

| 里程碑 | 建议版本 | 主要任务 | 退出条件 |
| --- | --- | --- | --- |
| M0 基线与基础 | 开发准备 | S01、S02，建立样本和回归清单 | Demo2.2可复现，迁移和新契约可验证 |
| M1 可靠输入 | Demo2.3 | T01至T04、T06，执行S03 | 识别可校对、问题可追问、冲突可定位，硬约束进入规划 |
| M2 日常与重排 | Demo2.4 | T05、T10、T11、T13，执行S02与S03 | 未完成和调课能提出重排，确认后保存，禁排约束持久生效 |
| M3 个性化闭环 | Demo2.5 | T07至T09、T12，执行S02与S03 | 用户档案影响方案，目标容量可核对，周报支持采纳改进 |
| M4 主动协商 | Demo3.0 | T14、T15，执行S02与S03 | 主动建议有事实依据、多轮方案可比较，频率可控 |

关键依赖：来源与学期规则 → 可靠课程事实 → 约束和规划 → 执行记录与重排 → 用户模型和复盘 → 主动协商。T13可在用户模型之前落地，先支持明确的禁排要求。

### 第一轮可直接执行的工作包

完成S01与S02的接口和迁移方案；准备T01标注样本；为T02建立周次和校历例外用例；实现T04的单次禁排约束，并用现有手工课表验证T06。识别服务尚在开发时，手工输入仍可用于验证约束和排程，避免相互阻塞。

### 分工与评审

产品负责人确认样本答案、规则边界及体验取舍；开发人员实现领域逻辑、界面、桌宠同步和迁移；测试人员维护标注与场景，检查实际落库结果。小团队可由同一人承担多种角色，每个阶段仍需保留独立可复核的验收证据。

计划以任务依赖和退出条件推进，不预设固定工期。M0结束后按实际样本复杂度、模型调用成本和开发投入估算各阶段工作量；需求变化需记录受影响任务、验收项和版本范围。

## 九 关键验收场景

以下场景为各阶段共同的最低验收集合，新增异常分支纳入对应任务测试。样例时间、课表和任务均采用隔离合成资料。

| 编号 | 场景与输入 | 必须观察到的结果 |
| --- | --- | --- |
| A01 | 截图含单双周、连堂和不清晰周次 | 可确定字段结构化；模糊项追问，未确认不进入正式课表 |
| A02 | 两页PDF重复同一课程，另有缺页 | 去重并提示范围不完整，不据此删除旧课程 |
| A03 | 同时段两门课程；跨校区只留10分钟、所需40分钟 | 分别报告时间重叠和转移不足；未知地点待补充 |
| A04 | 节假日校历缺失，用户提到顺延 | 询问学校调整规则，不自动推算补课日期 |
| A05 | 课程、午休和用户禁排占满可用时段 | 不突破硬约束；报告未安排任务及容量缺口 |
| A06 | 同一任务与课表，使用两份不同精力档案 | 合理改变时段选择，解释引用对应档案事实 |
| A07 | 计划60分钟，实际25分钟且任务未完 | 任务未完成、实际投入25分钟，重复提交不累计 |
| A08 | 任务未完后重复唤醒App并触发重排 | 生成一份有效建议；确认前不改正式日程 |
| A09 | 调课导致新冲突，部分安排已锁定 | 保留锁定项并提示冲突，仅提出必要调整 |
| A10 | 方案生成后另一端修改任务截止时间 | 拒绝保存过期方案，保留输入并要求重新计算 |
| A11 | 对话补充周三14点至17点禁排，然后重启 | 修改同一约束草稿；确认后持久生效，无重复事项 |
| A12 | 连续未执行任务，同时有执行记录缺失 | 缺失标为未知；建议可拆分或换时段，不擅自断言原因 |
| A13 | 周五放松与考试复习竞争；继续修改方案 | 展示可行替代及代价，选择前原安排不变 |
| A14 | 重复提醒、安静时段、桌宠完成与外部修改 | 去重和安静设置生效，保持无声，桌宠与日程一致 |
| A15 | Demo2.2旧资料升级后恢复备份 | 课程、任务、资料和配置可核对，新增记录默认值明确 |

每个场景记录前置数据、操作、期望、实际结果、对应提交及证据位置。识别准确率按T01单独评测；规划硬约束满足率须为100%，已知未解决冲突必须显式标记，不将无解任务计为已安排。

## 十 待确认事项与完成标准

### 实施前需要产品负责人决定的事项

| 决策事项 | 建议初始方案 | 确认节点 |
| --- | --- | --- |
| 首批课表样本和识别范围 | 图片及PDF合计至少30份、5种布局，先匿名化 | M0，影响T01 |
| 图片或PDF发送模型服务 | 沿用现有模型连接并明确告知上传内容；原件默认本地保存 | T01接入真实模型前 |
| 校历和跨校区耗时来源 | 用户确认校历，手工维护地点耗时，不默认调用地图 | T02与T03实现前 |
| 生活安排和休闲保护 | 用户先设作息，系统提出候选，确认后生效 | T05发布前 |
| 自动调整的授权范围 | 自动计算建议，正式日程逐次确认 | T11发布前 |
| 执行反馈与偏好学习 | 手工补记或自愿计时；推断建议先确认，不采集其他App行为 | T10与T09发布前 |
| 主动建议频率和安静时段 | 提供可关闭的设置，同一问题只在状态变化后再次提示 | T14发布前 |

以上为建议方案，不代表用户已经批准上传个人资料、采用默认作息或开启新的采集行为。没有确认的配置保持未启用，开发先用合成资料验证。

### 每项任务的完成标准

需求与例外分支已实现；对应数据可持久化并正确处理版本冲突和重复请求；有可复现的验收场景；界面和桌宠状态一致；升级路径通过验证；未完成范围在交付说明中明确。涉及正式安排变更时，须展示差异、确认结果和真实保存回执。

每个版本通过新增场景与既有回归，保留已知问题和未验证环境清单，交付可运行包、演示、迁移及恢复说明。阶段目标以退出条件验收，不按界面数量或对话表述判断完成。
