## 执行汇总：建议返回样例

以下字段名可在乙交付前共同冻结，示例不是甲新建的乙存储或现有端点。

```json
{
  "schema_version": 1,
  "data_revision": "execution-17",
  "items": [{
    "task_id": "真实任务ID",
    "step_id": "真实步骤ID",
    "block_id": "可选时间块ID",
    "actual_minutes": 25,
    "actual_minutes_known": true,
    "source": "manual",
    "completed": false,
    "incomplete_reason": "时间不够",
    "updated_at": "2026-10-29T18:00:00+08:00"
  }]
}
```

最低规则：`source`区分`timer/manual/legacy_estimate/unknown`；没有记录时`actual_minutes:null`，不能用0代替未知。更正后返回权威当前总量，不能把“原记录25分钟”和“更正20分钟”累计成45分钟。历史由计划时长写入的投入须标识为估算，不能冒充精确计时。明确这个总量是步骤累计还是单块累计，甲只减一次。标记完成、实际投入、点击网站是三个独立动作。

请至少给出：60分钟步骤实际25且未完成、缺记录未知、25更正为20、两条记录去重、任务完成但分钟未知等样例；附真实读写测试和重启恢复结果。

## 事件与版本：必须约定

- 提供可调用的函数/路由、输入输出及领域版本。事件复用甲的`record_change`，不要另起一套事件或保存机制。
- 影响规划的执行、更正、截止、档案、目标变化，调用`store.bump`进入全局source_revision；事实、事件、版本在同一事务，防止旧草稿继续确认。
- `event_type/source_id/source_revision`构成稳定去重身份。同版本重试不能多次累计；计划确认事件不得无限触发下一次重排。
- 明确开始/暂停、删除、撤销、修正、任务完成各自如何影响汇总和规划。甲不代写这些规则或猜实际投入。

## 档案与目标：缺数据时怎么返回

返回空对象/空列表或对应null，带版本和“未设置”状态，不提供伪默认个人习惯。只使用用户已确认的值，重置与撤回必须改变版本。偏好和目标可以分两次交付，优先给只读入口及3组固定样例；甲方用标明合成的数据开发消费端，不把它当真实联调。

至少提供两份不同已确认档案的读取结果、一份未设置档案；目标提供开启/暂停/超预算各一例。目标拆解复用现有任务与步骤，避免维护另一套同名待办。

## 乙可以立即复用的甲接口

- `GET /api/calendar-events`、`GET /api/occurrences`：实际课程分段，不把外边界整段占用。
- `POST /api/drafts/{id}/conflict-preview`：冲突、耗时未知及保存前版本检查。
- `POST /api/drafts/scheduling-constraint`：硬禁排/软偏好，单次/每周/有效期，原校对确认。
- `GET /api/planning-capacity`：今日/7天时间上限、可排工作与未排原因。
- `GET /api/replanning`、`POST /api/replan-drafts`：保留有效安排，变化预览/重排草稿。
- `GET /api/planning-options`、`GET /api/planning-risks`：双方案、取舍解释、容量和截止风险。
- `POST /api/plan-drafts`：选择策略`earliest|preferred`，可带expected_source_revision，仍需原确认。
- `POST /api/daily-routine-preview`、`/daily-routine-drafts`、`/daily-routine-dismiss`：显式规则候选，不生成第二套档案。
- 原`plan_snapshot`与`planning_event`：保留计划历史，不用最新计划覆盖旧快照。

精确字段以生成的`frontend/openapi.json`及甲接口说明为准。乙公共前端挂载、甲公共后端/API生成/发布仍按原分工。统一模型网关、统一Key入口，不新增第二套模型设置。
